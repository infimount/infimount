How it works

Storage should feel like one workflow, not twelve consoles.

Infimount keeps the familiar parts of a desktop file manager and adds the controls needed when storage is remote—or an AI agent is on the other side.

01

Connect the storage you already use

Add a local folder, bucket, drive, or remote file service. Validate reachability and backend capabilities before you rely on it.

02

Work with files normally

Browse, preview, search, upload, copy, move, compare, retry, and resolve conflicts from one desktop surface.

03

Share only what an agent needs

Expose selected storage and paths through MCP, choose read/write policy and tools, require confirmations, and keep a local audit trail.

The workbench

A file manager first. Storage infrastructure second.

The backend can change underneath you; the interaction does not have to. Infimount is built around finishing file operations without hiding capability differences.

  • ↗

    Browse, preview, and search

    Grid and list views, metadata, bounded previews, bookmarks, recents, keyboard navigation, and opt-in global search.

  • ⇄

    Dual-pane transfers

    Copy, move, compare, and update across supported storages without jumping between provider consoles.

  • ✓

    Transfer queue and conflict handling

    See progress, retry failures, cancel active work, and choose overwrite, discard, or keep-both behavior.

  • i

    Capability-aware operations

    Validate a backend and see read-only or unsupported operations before a mutation becomes a surprise.

Storage support

MCP access is off for new storages by default

Give an agent a room, not the house.

Infimount separates the desktop control plane from the MCP data plane. You decide which storage an agent can see, where it can go, what it can do, and which actions need confirmation.

Local-first control

Know where the boundary is.

Infimount is designed to make access state visible instead of asking you to trust a hidden service or a broad token.

No Infimount-hosted backend required

Storage sources, app configuration, MCP settings, and credential references live on your machine.

Native secret storage

Supported credentials move into the operating system secret store instead of a new plaintext fallback.

Signed updater chain

Every release requires cryptographically signed updater artifacts and key-correspondence checks.

OpenDAL-first backend layer

Storage operations stay behind a common abstraction with capability checks rather than custom provider shortcuts.
