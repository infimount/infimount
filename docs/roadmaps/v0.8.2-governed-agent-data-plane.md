# Infimount v0.8.2 Governed Agent Data Plane Implementation Plan

Status: active implementation plan  
Baseline: v0.8.1 stable plus the v0.8.2 product-direction documentation branch  
Target stable release: v0.8.2  
Version policy: v0.8.2 is the long-running feature train. No v0.9 release is planned for roughly the next year.

## 1. Objective

v0.8.2 turns the v0.8.1 Agent Task proof into an agent-neutral governed data plane.

Infimount should own the boundary around agent work:

~~~text
systems of record
        |
        v
explicit source selection
        |
        v
snapshot + hashes + provenance
        |
        v
bounded task workspace
        |
        +-------------------------------+
        |                               |
        v                               v
local MCP client                 remote sandbox/runtime
Codex / Claude /                 OpenAI / Daytona /
OpenCode / Gemini / Pi           Modal / future runtimes
        |                               |
        +---------------+---------------+
                        |
                        v
                  task outputs
                        |
                        v
              review + exact hashes
                        |
                        v
            explicit publication plan
                        |
                        v
          verified create-only write-back
                        |
                        v
              publication receipt
                        |
                        v
                systems of record
~~~

The v0.8.2 goal is not “support more agents” as an integration checklist. The goal is to make agent identity and runtime choice replaceable without changing the task data contract, storage authorization model, review model, or publication safety boundary.

## 2. Versioning contract

All feature work in this plan targets v0.8.2.

The stable tag v0.8.2 must remain immutable once published. Therefore the long development train uses prerelease checkpoints:

- v0.8.2-alpha.N for agent-neutral execution and early local adapters.
- v0.8.2-beta.N for headless control surfaces, MCP Apps, and sandbox integrations.
- v0.8.2-rc.N after the planned feature surface is complete and qualification begins.
- v0.8.2 only after the full release matrix passes.

No v0.9 tag is part of this plan.

This avoids a false choice between “one giant hidden branch for a year” and “jump version numbers for each feature.” Users can test v0.8.2 prereleases while v0.8.1 remains the stable channel until v0.8.2 is genuinely ready.

## 3. v0.8.1 baseline we must preserve

v0.8.1 established the trust model. v0.8.2 must extend it, not replace it.

The following are hard compatibility requirements:

1. OpenDAL remains the storage I/O abstraction.
2. Task preparation never mutates selected source bytes.
3. Preparing a task never broadens source-storage MCP exposure.
4. Inputs are copied into a bounded task package and hashed.
5. The task-scoped MCP server remains independently scoped from general Agent Access.
6. Local Agent Task writes are limited to the task output boundary.
7. Original source/workspace host paths are not handed to the agent.
8. Output review re-hashes the actual bytes being shown.
9. Publication begins with nothing selected.
10. Publication supports create-only fail-or-rename behavior, never overwrite.
11. Publication previews are stale-state fingerprints, not reusable write authority.
12. Apply rebuilds and revalidates the publication plan.
13. Destination bytes are verified after commit.
14. Successful publication creates a unique receipt.
15. Secrets remain in native secret storage and do not appear in task evidence.
16. Existing v0.8.1 task packages and receipts remain readable.

Any adapter or runtime that cannot preserve these invariants does not ship.

## 4. Core design decision: Task is not Execution

v0.8.1 currently has an agent-neutral task manifest but a Codex-specific handoff implementation. v0.8.2 formalizes a separation that already exists conceptually.

### Agent Task

The task is the immutable work contract:

- task ID
- title/objective
- prepared input paths
- input byte sizes and hashes
- workspace binding
- output directory contract

The task must remain independent of the client or runtime that executes it.

Do not add fields such as claudeVersion, codexVersion, sandboxProvider, model, or executablePath to the Agent Task manifest.

### Agent Execution

An execution is one attempt to complete a task with a particular client/runtime.

Execution identity belongs in a separate record.

Proposed private record location inside the Agent Workspace:

~~~text
.infimount/
  workspace.json
  task-executions/
    <task-id>/
      <execution-id>.json
~~~

This location is outside the task-scoped MCP prefix, so an agent cannot rewrite its own execution evidence.

### Execution record v1

Required safe fields:

- schemaVersion
- executionId
- taskId
- workspaceId
- adapterKind
- adapterVersion
- executableSha256 when a local executable is used
- runtimeKind: local_client or remote_sandbox
- runtimeProvider when applicable
- startedAt
- finishedAt
- status: prepared, running, succeeded, failed, cancelled
- taskScopeDigest
- enabledTaskTools
- isolationProfile
- promptSha256
- outputFileCount
- outputTotalBytes
- outputAggregateSha256
- safe errorCode when failed
- opaque runtimeExecutionId when a provider supplies one

The record must not contain:

- credentials
- bearer/API tokens
- storage configuration JSON
- original source host paths
- workspace host paths exposed to the agent
- source file contents
- raw environment variables
- full captured prompts when they may contain private data

### Execution/output rule for v0.8.2

Keep the v0.8.1 outputs/ layout for compatibility.

A task may have multiple failed/cancelled execution attempts while outputs remain empty. Once an execution has produced reviewable outputs, another execution must not silently reuse or overwrite those output paths.

For v0.8.2, the safe user action for a second independent run is to prepare a new task from the same source selection. Execution-scoped output directories are deliberately deferred until there is a concrete product need because changing the task layout would create unnecessary migration and publication complexity.

## 5. Two adapter families, not one leaky abstraction

Local MCP clients and remote sandboxes have different trust semantics. Do not force them behind one implementation interface.

### 5.1 Local Agent Adapter

Used by:

- Codex
- Claude Code
- OpenCode
- Gemini CLI
- Pi
- future local MCP clients

Responsibilities:

1. Detect the exact executable.
2. Canonicalize its path.
3. Hash the executable.
4. Probe and record its version.
5. Revalidate executable identity immediately before launch.
6. Build a neutral working directory.
7. Configure exactly one task-scoped Infimount MCP server.
8. Disable or deny ambient execution/data surfaces.
9. Launch and capture bounded, privacy-safe execution status.
10. Terminate the process tree on timeout/cancel.
11. Write an execution record.

The adapter does not get to change task scope or storage policy.

### 5.2 Sandbox Runtime Adapter

Used by:

- OpenAI Sandboxes
- Daytona
- Modal
- future isolated execution providers

Responsibilities:

1. Create a sanitized task bundle from the prepared task.
2. Never upload source storage credentials or source configuration.
3. Never mount the original source storage directly.
4. Provision an isolated runtime.
5. Upload only the sanitized prepared task bundle.
6. Execute the task with a bounded output contract.
7. Download only the output tree and safe execution metadata.
8. Reject symlinks/reparse-point escapes, invalid paths, excessive file counts, excessive bytes, and path collisions.
9. Import output files create-only into the local Agent Task outputs directory.
10. Write a private execution record.
11. Tear down or explicitly retain the runtime according to user policy.

A sandbox provider is compute. Infimount remains the authority for data ingress and egress.

## 6. Sanitized sandbox bundle

The current Agent Task manifest contains Infimount storage identity fields that are useful locally but should not be exported to remote runtimes.

Do not upload the raw local task manifest to a remote provider.

Create a separate SandboxTaskBundle manifest containing only:

- bundle schema version
- task ID
- task title/objective
- relative input paths
- byte sizes
- SHA-256 hashes
- expected output directory
- safe task instructions
- bundle aggregate SHA-256

Explicitly exclude:

- source storage ID
- source storage name when it is private
- MCP exposure state
- workspace storage ID
- storage namespace fingerprints
- local host paths
- secrets
- destination publication information

The remote runtime receives a data room, not authority to the source system.

Target shape:

~~~text
Tauri UI                         infimountctl

                   |

                   |
       +-----------+------------+
       |                        |

task preparation/review    execution coordinator
/publication                     |

       |               |                    |
       |               v                    v
       |        local adapters       sandbox adapters
~~~

The desktop and headless surfaces must call the same trusted services. Do not copy the v0.8.1 Tauri command logic into a second CLI implementation.

## 8. Shared control-service extraction

Do not begin with a large rewrite of every Tauri command.

Use a staged extraction:

1. Extract Agent Task handoff validation first.
2. Prove Codex parity through the generic path.
3. Add a second adapter (Claude Code) to validate the abstraction.
4. Then introduce a shared crate for the stable task control surface.

Proposed crate:

~~~text
crates/control/
  src/
    task_prepare.rs
    task_review.rs
    task_publish.rs
    execution.rs
    local_adapters/
    sandbox_adapters/
~~~

Package name: infimount_control.

Tauri commands become thin authorization/UI wrappers around this crate.

infimountctl uses the same crate.

The MCP data plane does not import the control crate.

This keeps the authorization directions clear:

~~~text
desktop / CLI -> control plane -> storage + task state
agent          -> task MCP      -> bounded task data
~~~

## 9. Local adapter requirements

### 9.1 Codex

Codex is the golden parity adapter.

The first refactor must preserve the exact v0.8.1 security posture:

- neutral temporary CWD
- read-only Codex sandbox
- code mode disabled
- code-mode host enabled only because current Codex requires it for MCP routing
- shell disabled
- unified exec disabled
- shell snapshot disabled
- permission/request tools disabled
- hooks disabled
- browser/computer use disabled
- plugins/apps disabled
- project docs/skills/memories disabled
- web search disabled
- only the task-specific Infimount MCP server required
- six-tool Agent Task allowlist
- no source/workspace host path in the prompt

Add golden argument/config tests before moving code out of codex_handoff.rs.

### 9.2 Claude Code

Claude Code is the first new first-class adapter because the current CLI exposes the controls required for a fail-closed non-interactive launch.

Required launch posture:

- non-interactive print mode
- restricted mode
- bare/minimal configuration mode where compatible
- no session persistence
- explicit task MCP configuration
- strict MCP configuration so ambient MCP servers are ignored
- built-in tool set disabled
- exact task MCP tools explicitly allowed
- unattended permission prompts disabled/denied
- browser integration disabled
- neutral CWD
- no source host path
- exact executable/version/digest recorded

Minimum supported Claude Code version must be derived from the flags we depend on and enforced by detection. Do not silently fall back to a less restrictive configuration on older versions.

Real packaged regression must prove:

- MCP connects
- outputs are produced through Infimount write_file/mkdir only
- no Bash/Edit/host Read tool was available
- no unrelated MCP server loaded
- source digest/exposure remain unchanged

### 9.3 OpenCode

OpenCode is feasible but permissive by default, so the adapter must be deny-first.

Required posture:

- neutral CWD with no project configuration
- generated isolated config
- permission catch-all deny
- exact task MCP tools allow
- built-in edit/write/bash/web/subagent/skill/plugin surfaces denied unless a future task contract explicitly requires them
- only the task MCP server enabled
- no external directory permission
- no session sharing
- exact executable/version/digest recorded
- process-tree cleanup on timeout/cancel

The adapter does not ship if global/managed configuration can re-enable an ambient write surface that our generated restrictions cannot override.

### 9.4 Gemini CLI

Gemini CLI ships only after a capability spike proves a fail-closed configuration.

Known constraints to design around:

- headless -p mode is available
- structured JSON/stream-JSON output exists
- sandboxing exists
- explicit allowed MCP server names exist
- approval modes and a policy engine exist
- Plan Mode is read-only and cannot serve as the writable task execution mode
- confirmation-dependent tool behavior can make unattended execution stall or deny

The adapter must establish an explicit policy that denies shell and local file mutation while allowing only the task MCP tools needed to write outputs.

Do not use YOLO as the security mechanism.

If the current Gemini CLI cannot provide a deterministic deny-first configuration for non-interactive task execution, keep the adapter experimental and do not promote it into the stable v0.8.2 adapter matrix.

### 9.5 Pi

Reuse the existing Pi integration instead of building a second configuration path.

The v0.8.2 Pi adapter should:

- receive a task-specific MCP server configuration
- use the same six-tool task allowlist
- avoid general Infimount storage exposure
- emit the common execution record
- preserve the task output/review/publication flow

Pi remains an adapter, not a special execution architecture.

## 10. Headless control surface

### 10.1 infimountctl

Add a first-party binary named infimountctl.

Required command groups:

~~~text
infimountctl task preflight
infimountctl task prepare
infimountctl task list
infimountctl task execute
infimountctl task execution
infimountctl task review
infimountctl task publish-preview
infimountctl task publish-apply
infimountctl task evidence
~~~

Requirements:

- human-readable output by default
- --json for machine-readable output
- stable JSON schema/version
- no secrets or full source host paths in JSON
- same validation and state locks as desktop
- no broad --yes flag that bypasses publication review
- publish-apply requires the exact preview token and exact reviewed output hashes
- failures use stable error codes and non-zero exit status
- cancellation terminates local execution trees and updates the execution record

### 10.2 Local control API

Add only after infimountctl proves the shared control crate.

Initial transport:

- Unix domain socket on Linux/macOS
- Windows named pipe on Windows

Do not expose a TCP control API in the initial v0.8.2 implementation.

Reasons:

- local-first trust model
- no port discovery or LAN exposure
- OS-local access control
- smaller authentication surface

The API is for trusted local automation, not for models. MCP remains the agent-facing data plane.

## 11. MCP Apps review and publication UX

MCP Apps can make the strongest Infimount workflow available inside compatible agent hosts without moving storage authority into the host.

Initial tools:

### Model-visible

- show_task_review

This returns safe summary data and a ui:// resource.

### App-only

- get_task_output_chunk
- refresh_task_review
- preview_task_publication
- apply_task_publication

The publication apply tool must be registered only with app visibility. The model must not see or call it.

Additional safety requirements:

1. Host must advertise MCP Apps capability.
2. Host must honor app-only tool visibility.
3. If those capabilities are absent, final apply is not registered and the UI degrades to review-only.
4. Apply still requires the exact server-generated preview token.
5. Apply still re-hashes outputs and rebuilds the destination plan.
6. UI starts with nothing selected.
7. No overwrite option exists.
8. The UI never receives storage credentials or source host paths.
9. Destination storage choices use safe display identity only.
10. Desktop and infimountctl remain authoritative fallbacks.

This makes MCP Apps a portable approval surface without turning normal model tool calls into publication authority.

## 12. Remote sandbox integration contract

Every sandbox adapter follows the same sequence:

~~~text
prepared local task
      |
      v
build sanitized bundle
      |
      v
hash bundle
      |
      v
provision sandbox
      |
      v
upload bundle
      |
      v
run agent
      |
      v
download outputs to local staging
      |
      v
validate paths/counts/bytes/hashes
      |
      v
create-only import to task outputs/
      |
      v
execution record
      |
      v
normal Infimount review/publication
~~~

### Output import rules

Before importing remote outputs:

- reject absolute paths
- reject .. traversal
- reject symlink/reparse-point objects
- reject control characters
- reject case-insensitive collisions
- enforce the existing Agent Task output file-count limit
- enforce the existing aggregate byte limit
- hash every file
- stage locally before task mutation
- fail if a destination output path already exists
- never delete or overwrite a previous output

If import partially commits, surface cleanup-required state exactly as publication does. Never hide partial state.

## 13. Sandbox adapters

### 13.1 OpenAI Sandbox

First sandbox adapter.

Use a fresh sandbox/task workspace contract.

Infimount provides:

- sanitized task files
- task instructions
- output directory expectation

Infimount does not provide:

- source storage credentials
- destination credentials
- original source host paths
- general Agent Access credentials

Retrieve outputs after execution and import them through the common output-import validator.

Provider credentials use native secret storage.

### 13.2 Daytona

Second sandbox adapter.

Use Daytona filesystem APIs for upload/download rather than shelling out when possible.

Snapshots are optional optimization, not part of authorization.

If snapshots/warm pools are used:

- snapshot identity belongs in the execution record
- a snapshot must never contain source credentials
- a reused runtime must begin with a fresh task data directory
- output from a previous task must not leak into a new task

### 13.3 Modal

Third sandbox adapter.

Use the filesystem API and sandbox lifecycle primitives.

Do not make snapshot/exit-snapshot behavior required for correctness because provider snapshot behavior can be best-effort or lifecycle-specific.

The durable Infimount evidence is the local execution record plus imported output hashes, not the provider snapshot.

## 14. Identity, provenance, audit, and receipts

v0.8.2 should make the execution chain inspectable:

~~~text
task manifest
   |
   v
execution record
   |
   v
review snapshot
   |
   v
publication preview
   |
   v
publication receipt
~~~

### Publication receipt v2

New receipts should add:

- executionId
- adapterKind
- taskScopeDigest
- reviewedOutputAggregateSha256

Continue reading v1 receipts.

Do not rewrite historical receipts.

### Audit events

Add privacy-safe lifecycle events:

- agent_task_execution_prepared
- agent_task_execution_started
- agent_task_execution_succeeded
- agent_task_execution_failed
- agent_task_execution_cancelled
- agent_task_reviewed
- agent_task_publication_previewed
- agent_task_published

Events may contain:

- adapter kind
- backend kind
- counts
- byte totals
- opaque task/execution IDs
- safe result/error codes

Events must not contain:

- source contents
- prompts
- host paths
- secrets
- provider tokens

### MCP identity direction

Track MCP agent-identity and workload-identity standards, but do not invent an Infimount-specific enterprise identity protocol.

v0.8.2 should preserve identity fields in extensible records so later workload identity or delegated-principal claims can be attached without changing the task data model.

SSO, organization policy distribution, and a hosted enterprise control plane are not v0.8.2 requirements.

## 21. v0.8.2 stable acceptance criteria

v0.8.2 can become stable only when:

1. v0.8.1 upgrade path remains green.
2. All source/task/publication safety invariants remain green.
3. Codex and Claude Code packaged real-task pilots pass.
4. Every other adapter documented as stable passes its packaged real-task pilot.
5. Headless CLI has publication parity with desktop.
6. Local IPC API has the same authorization and stale-preview semantics.
7. MCP Apps cannot expose model-callable final publication authority.
8. At least one sandbox adapter passes coding, document, and data-analysis scenarios before sandbox execution is marketed as stable.
9. Every advertised sandbox provider passes its provider-specific qualification.
10. Source digest and MCP exposure remain unchanged across every real pilot.

## 22. Explicit v0.8.2 non-goals

Do not expand this train into:

- a generic MCP gateway
- a general agent marketplace

- a Kubernetes/compute scheduler
- a vector database or RAG platform
- a mobile app

## 23. Ecosystem constraints this plan intentionally follows

As of October 2026:

- Claude Code supports non-interactive execution, explicit/strict MCP configuration, restricted mode, built-in tool restriction, no-session-persistence, and unattended permission-prompt denial. The adapter should use those controls rather than trust a neutral directory alone.
- OpenCode supports non-interactive run mode, explicit MCP configuration, custom config paths/directories, and deny/ask/allow permission rules. Its permissive defaults mean Infimount must install an explicit deny-first policy.
- Gemini CLI supports headless structured output, sandboxing, explicit MCP server allowlists, approval modes, and a policy engine. Its adapter therefore requires a capability/policy proof rather than a permissive “YOLO” launch.
- MCP Apps supports sandboxed interactive UI resources and app-only tools hidden from the model. That gives Infimount a portable review/approval surface while retaining the exact publication token checks.
- OpenAI Sandboxes, Daytona, and Modal provide isolated filesystems/runtime environments. Infimount should integrate with these compute layers instead of implementing another sandbox platform.
- The MCP roadmap is moving toward long-running tasks, agent identity, workload identity/delegation, and enterprise security. Infimount should keep its execution/provenance records extensible rather than inventing a private identity standard.

These are integration constraints, not dependencies on any one vendor.
